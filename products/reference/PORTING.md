# Porting Secular to hardware (RK35xx)

Secular's supported board is **qemu-arm64 virt**. This note is the map for
bringing the same serial-console image up on a real ARM64 SoC, using Rockchip
RK356x / RK3588 (RK35xx) as the worked example.

The product stays the same:

```text
zircon kernel + linux-arm64-boot-shim + BOOTFS + serial console + zxsh
```

Do not grow the tree into a full Fuchsia product (graphics, netstack, WLAN,
update, recovery). A hardware port that cannot print kernel logs and drop to
`zxsh` on UART has not succeeded.

## What QEMU already gives you

```text
U-Boot-compatible Image          linux-arm64-boot-shim.bin
Linux boot protocol (x0 = DTB)
         │
         ▼
     secular.zbi                 kernel + BOOTFS
         │
         ▼
userboot → component_manager → console-launcher → zxsh
```

QEMU launch (`make run`) is:

```text
qemu-system-aarch64 -kernel linux-arm64-boot-shim.bin -initrd secular.zbi
                    + virt DTB + ATF (EL2) + GICv3 + PL011
```

`linux-arm64-boot-shim` (`zircon/kernel/arch/arm64/phys/boot-shim/`) is a
Linux `Image`: it reads the DTB in `x0`, finds RAM / GIC / UART / PSCI,
appends those as ZBI items, and jumps into Zircon. The ZBI is the ramdisk
(`linux,initrd-*`).

RK35xx U-Boot speaks the same protocol (`booti`). The shim and ZBI do not
need to be rebuilt as a Rockchip-specific image format.

## What a board actually is here

GN today always imports QEMU:

```text
tools/secular-boot/configure.sh
  import("//products/boards/qemu-arm64.gni")
  import("//products/secular.gni")

products/secular/BUILD.gn
  assert(current_cpu == "arm64")   # CPU, not "only QEMU"
```

| Piece | QEMU virt | RK35xx |
| --- | --- | --- |
| `target_cpu` | arm64 | arm64 (same kernel port) |
| Boot CPU | Cortex-A57/A72 model | A55 (RK356x) or A76+A55 (RK3588) |
| Interrupt | GICv3 | GICv3 |
| Debug UART | PL011 | DesignWare 8250 (`snps,dw-apb-uart`) |
| RAM base | `0x40000000` | usually `0x00000000` (see vendor DTB) |
| Firmware | QEMU ATF BIOS (EL2) | BootROM → idbloader → TF-A + U-Boot |
| DTB | generated by QEMU | vendor `.dtb` (or a trimmed copy) |
| Userspace UART driver | none; kernel serial syscalls | none, if kernel UART works |

Console-launcher talks to the kernel serial (`kernel.enable-serial-syscalls=true`),
not to a board UART driver in userspace. If phys + kernel can print on the SoC
UART, `zxsh` comes up without new devices.

## UART: why RK often works without a new driver

Zircon phys/kernel UART matching is in `zircon/system/ulib/uart`. The shim
walks `/chosen/stdout-path` (see `devicetree-chosen-matcher.cc`).

RK vendor DTB typically looks like:

```dts
chosen {
    stdout-path = "serial2:1500000n8";
};

uart2: serial@fe660000 {
    compatible = "rockchip,rk3568-uart", "rockchip,rk3066-uart",
                 "snps,dw-apb-uart";
    reg-shift = <2>;
    reg-io-width = <4>;
};
```

`uart::dw8250::Driver` binds `snps,dw-apb-uart` **only if** `reg-io-width = 4`
and `reg-shift = 2` (`dw8250.h`). That is the usual Rockchip layout. If the
DTB omits those properties, the shim will not select the UART and you get
silence — fix the DTB, do not write a new driver first.

U-Boot must leave the UART clocks and pinctrl enabled. It almost always does
if you can already see U-Boot on the same header.

## Boot chain on RK35xx

```text
BootROM
  → idbloader.img (TPL/SPL)
    → u-boot.itb  (TF-A BL31 + U-Boot)
      → booti
           kernel  = linux-arm64-boot-shim.bin   (Linux Image)
           initrd  = secular.zbi
           fdt     = rk3588-<board>.dtb
```

Example U-Boot script (addresses from the vendor `boot.cmd`; do not copy
these numbers blindly):

```text
load mmc 1:1 ${kernel_addr_r}  linux-arm64-boot-shim.bin
load mmc 1:1 ${ramdisk_addr_r} secular.zbi
load mmc 1:1 ${fdt_addr_r}     rk3588-evb.dtb
booti ${kernel_addr_r} ${ramdisk_addr_r}:${filesize} ${fdt_addr_r}
```

`${filesize}` must be the ZBI size, not the DTB size. Load the ZBI last or
save `filesize` after that `load`.

Artifacts after `make build` (arm64):

| File | Role on the board |
| --- | --- |
| `out/secular-boot-arm64/linux-arm64-boot-shim.bin` | U-Boot "kernel" |
| `out/secular-boot-arm64/secular.zbi` | U-Boot ramdisk |
| vendor `*.dtb` | U-Boot FDT (`x0`) |

Keep vendor U-Boot until serial works. Replacing TF-A/U-Boot is a later
problem (EL2, PSCI, clocks).

## Recommended sequence

### 0. Keep QEMU green

`make verify` on qemu-arm64 must still pass. Hardware work is additive.

### 1. Confirm the SoC on a known OS

From Linux or U-Boot on the same board, record:

- UART MMIO, IRQ, `compatible`, `reg-shift`, `reg-io-width`, baud
- `/chosen/stdout-path`
- memory `reg` (base and size)
- GIC compatible (`arm,gic-v3`)
- whether U-Boot `booti` already boots a Linux `Image` + initrd + DTB

If Linux does not print on that UART, Secular will not either.

### 2. First boot: reuse the qemu-arm64 ZBI

Do not fork the product yet. Flash or TFTP:

1. `linux-arm64-boot-shim.bin`
2. `secular.zbi` from the qemu-arm64 build
3. the **board** DTB, not QEMU's

Watch the UART at the U-Boot baud (often 1.5 Mbaud on Rockchip, not 115200).

Expected, in order:

1. Shim symbolizer / phys UART
2. Zircon `starting *` / `PHYSBOOT`
3. userboot
4. `component_manager`
5. `console-launcher` / `zxsh` prompt

If (1) never appears: DTB UART match, clocks, or `booti` argument order.
If (1) works and (2) hangs: RAM map or cache. If (5) is missing: cmdline
(`console.shell`, `kernel.enable-serial-syscalls`) is already in
`products/secular/BUILD.gn` and should not need a board fork.

### 3. Only then add a board GN file

When the qemu-arm64 ZBI actually runs on the SoC, add a thin board:

```text
products/boards/rk3588.gni          # target_cpu = "arm64", board_is_emu = false
products/boards/rk3588/BUILD.gn     # optional; do not import vim3/arm64 assembly
```

`rk3588.gni` should look like `qemu-arm64.gni` with emulation flags off:

```gn
has_board = true
target_cpu = "arm64"
board_name = "rk3588"
board_is_emu = false
```

Point configure at it (today `configure.sh` hard-codes qemu-arm64):

```sh
# sketch — not implemented
import("//products/boards/${BOARD}.gni")   # BOARD=rk3588
import("//products/secular.gni")
```

Keep `ARCH=arm64`. RK35xx is not a second CPU port.

Leave `assert(current_cpu == "arm64")` in `products/secular/BUILD.gn`. Change
comments that say "qemu-arm64 only" to "arm64". Do not copy
`products/boards/arm64.gni` (AVB keys, Bazel assembly, virtio).

### 4. Kernel / phys only if the DTB is not enough

Touch Zircon only with a failing boot log in hand:

| Symptom | Where |
| --- | --- |
| No phys output, DTB has `snps,dw-apb-uart` but no `reg-shift` | Fix DTB, or relax `dw8250::TrySelect` |
| UART works in U-Boot, silence after `booti` | stdout-path; clocks gated |
| Panic in MMU / phys allocation | memory nodes; `generate_peripheral_ranges` |
| Secondary CPUs stuck | PSCI in TF-A; `cpu-enable-method` |
| `zx_guest_create` fails | kernel not in EL2 / no VHE; ignore until console works |

Do not add SoC clock, pinctrl, or CRU drivers for the first console. U-Boot
must leave UART alive.

### 5. Userspace last

No new UART driver is required for `zxsh`. Add board drivers only when a
later milestone needs them (storage, then maybe net). Hypervisor
(`userspace/hypervisor`) is optional and wants EL2.

## Out of scope for a first RK image

- GPU / HDMI / NPU / camera / audio
- Ethernet, WLAN, Bluetooth
- eMMC/UFS as a Fuchsia filesystem (use the same media as a U-Boot boot
  partition only)
- AVB / vbmeta / recovery / OTA
- New CPU architectures (RK35xx is arm64)
- Vendoring TF-A, U-Boot, or `prebuilt/` into this tree
- Copying Fuchsia `vim3` / `nelson` / `qemu-arm64` assembly boards wholesale

## Checklist

- [ ] `make verify` still passes on qemu-arm64
- [ ] UART MMIO, baud, and `stdout-path` recorded from Linux/U-Boot
- [ ] Vendor DTB has `snps,dw-apb-uart` plus `reg-io-width = <4>` and
      `reg-shift = <2>`
- [ ] U-Boot `booti` with shim + `secular.zbi` + board DTB
- [ ] Phys serial, then Zircon, then `zxsh`
- [ ] Board `.gni` only after that boot works
- [ ] No extra product features
